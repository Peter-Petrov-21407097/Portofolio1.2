Pórtfólio - V1.2

Arquitetura Model View Template do Django

Esta aplicação foi desenvolvida com Django e segue a arquitetura MVT: Model, View e Template.A ideia foi tentar usar a logica aprendida em aulas, assim como os conhecimentos exteriores à universidade, para desenvolver um Pórtfólio.

2. Modelação

Modelo de dados utilizado nesta aplicação Django.

Diagrama Entidade-Relação

O diagrama entidade-relação representa as principais entidades da aplicação e as relações entre elas. Neste projeto existem entidades como Licenciatura, Unidade Curricular, Projeto, Tecnologia, Competência, Formação, Área de Interesse, TFC, Making Of, Mídia e Docente.

Modelação em models.py

A modelação da aplicação foi implementada no ficheiro models.py, usando classes Django que herdam de models.Model. Cada classe representa uma tabela da base de dados e cada atributo representa um campo.

A classe Licenciatura representa o curso e está relacionada com várias Unidades Curriculares. Cada unidade curricular pode ter vários Projetos, Docentes, ficheiros de Mídia e registos de Making Of.

A classe Projeto é uma das entidades centrais da aplicação. Cada projeto pertence a uma unidade curricular e pode estar associado a uma área de interesse. Além disso, pode ter várias tecnologias e competências, através de relações ManyToManyField.

As classes Tecnologia e Competência permitem descrever ferramentas, linguagens e capacidades desenvolvidas. Estas entidades são reutilizadas em projetos, formações e TFCs, evitando repetição de dados.

A classe MakingOf serve para documentar o processo de desenvolvimento, incluindo decisões tomadas, erros encontrados, correções realizadas, justificação da modelação e utilização de IA. Esta classe está ligada opcionalmente a projetos, unidades curriculares, tecnologias, TFCs, formações e competências.

A classe Midia permite guardar ficheiros, imagens ou recursos relacionados com diferentes partes do portefólio. Já a classe Docente representa professores e pode estar associada a várias unidades curriculares.

Relações principais(mas nao todas, as imagens do caderno em midia tem todas)

  • Licenciatura → UnidadeCurricular: uma licenciatura pode ter várias unidades curriculares.
  • UnidadeCurricular → Projeto: uma unidade curricular pode ter vários projetos.
  • Projeto ↔ Tecnologia: um projeto pode usar várias tecnologias e uma tecnologia pode ser usada em vários projetos.
  • Projeto ↔ Competência: um projeto pode desenvolver várias competências e uma competência pode estar presente em vários projetos.
  • Formação ↔ Tecnologia/Competência: uma formação pode estar associada a várias tecnologias e competências.
  • ÁreaInteresse → TFC/Projeto: uma área de interesse pode agrupar TFCs e projetos.
  • Docente ↔ UnidadeCurricular: um docente pode lecionar várias unidades curriculares.
  • Docente ↔ UnidadeCurricular: um docente pode lecionar várias unidades curriculares.

3. Tecnologias

Tecnologias utilizadas na construção da aplicação Django.

Esta aplicação foi desenvolvida com várias tecnologias de frontend, backend, base de dados, versionamento e alojamento de código. As tecnologias estão registadas na classe Tecnologia e devem estar associadas ao projeto Portfolio de Programação Web.

Frontend

  • HTML: usado para estruturar as páginas da aplicação.
  • CSS: usado para definir o aspeto visual, layout, cores e organização dos conteúdos.

Backend

  • Python: linguagem principal usada no desenvolvimento da aplicação.
  • Django: framework web usada para criar os modelos, views, templates, rotas e formulários.

Base de dados

  • SQLite: base de dados usada durante o desenvolvimento do projeto.

Storage / Media

  • MEDIA_ROOT e MEDIA_URL: usados para guardar e apresentar imagens, PDFs e outros ficheiros carregados na aplicação.

Outros

  • Git: usado para controlar versões do código.
  • GitHub: usado para alojar o repositório online e manter o histórico do projeto.
  • GitHub Codespaces: ambiente de desenvolvimento online usado para editar e executar o projeto.

6. Making-Of

Registo do processo de desenvolvimento da aplicação.

O Making-Of reúne apontamentos sobre o desenvolvimento do projeto, incluindo dificuldades encontradas, decisões tomadas, alterações feitas à modelação, utilização de tecnologias e melhorias implementadas ao longo das semanas.

Nesta fase, o objetivo é apresentar uma visão geral do processo de construção da aplicação. Posteriormente, poderá existir uma página própria com todos os detalhes registados na tabela MakingOf.

Os registos do Making-Of ajudam a documentar a evolução do projeto e a explicar não só o resultado final, mas também o processo seguido para chegar à aplicação atual.

Ver registos de Making Of na página inicial

Model

O Model representa os dados da aplicação. Neste Portfolio, os modelos definem uma das 11 possíveis entidades que foram aceites e implementadas na modelação inicial, baseado nos requerimentos pedidos e com base em experiência pessoal.

View

A View recebe o pedido do utilizador. Tambem podemos consultar, alterar, apagar qualquer tipo de informação através dos Models e é esta mesmissima view que seleciona o template que é mostrado

Template

O Template é responsável pela apresentação da informação ao utilizador, usandos diferentes fontes. Vamos utilizar HTML para adquirir esta informação de forma organizada, assim como variáveis para apresentar um aspecto limpo.

Fluxo de informação

O utilizador acede a um URL. O Django procura esse caminho no ficheiro urls.py. Chama a View correspondente. A View interage com os Models e envia os dados para um Template. Por fim, o Template gera a página HTML apresentada no browser.
